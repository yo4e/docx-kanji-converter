# docx-kanji-converter

Word（`.docx`）形式の日本語小説原稿に、定型的な文字変換と書式調整を行う試作スクリプトです。

> [!CAUTION]
> 現在は実験段階です。入力・出力パスがコードに固定されており、変換は文脈を考慮しません。必ず原稿のバックアップを残し、出力結果を確認してください。

## 現在の処理内容

`main.py` は `python-docx` で文書を開き、`doc.paragraphs` に含まれる段落とRunを順番に処理します。

### 1. 本文段落の字下げ

次のいずれにも該当しない段落では、最初のRunの先頭に全角スペースを1字追加します。

- 段落スタイル名が `見出し` で始まる
- 段落スタイル名が `Heading` で始まる
- 段落本文が `「` で始まる
- 段落本文が `（` で始まる
- 段落本文が `『` で始まる

Runを持たない空段落には追加しません。

### 2. 半角数字の漢数字化

連続する半角数字（正規表現 `\d+`）を漢数字へ変換します。

例：

- `0` → `零`
- `11` → `十一`
- `22` → `二十二`
- `100` → `百`

現在の変換関数は最大4桁を想定しています。5桁以上の数値は安全に処理できません。

### 3. 三点リーダーの置換

半角ピリオド3文字の `...` を `……` に置換します。

Unicodeの三点リーダー `…` 単体は、現在のコードでは置換対象ではありません。また、3文字が複数のRunに分かれている場合は置換されません。

### 4. 半角英字の全角化

半角の英字 `A-Z` と `a-z` を、対応する全角英字へ変換します。

数字、記号、空白はこの処理では変換しません。

### 5. 感嘆符・疑問符後の空白挿入

`！` または `？` の直後に全角スペースを追加します。ただし、直後が次の文字の場合は追加しません。

- 全角スペース
- `）`
- `」`
- `』`

### 6. 斜体を太字へ変更

Runが斜体の場合、斜体を解除して太字に変更します。

### 7. フォント設定の調整

すべてのRunで `run.font.name` を `None` に戻します。

その後、段落スタイル名が `見出し` または `Heading` で始まらない段落について、すべてのRunのフォントサイズを12ptに設定します。

## 現在の使い方

### 必要なもの

- Python
- `python-docx`

```bash
pip install python-docx
```

### 実行

現状では、`main.py` 内の次のパスを使用環境に合わせて直接書き換える必要があります。

```python
doc = Document("/Users/a104/Desktop/input.docx")
```

```python
doc.save("/Users/a104/Desktop/output.docx")
```

その後、スクリプトを実行します。

```bash
python main.py
```

## 処理対象の範囲

現在処理するのは、`doc.paragraphs` から取得できる通常の本文段落です。

次の要素は未検証、または処理対象外です。

- 表内の段落
- ヘッダーとフッター
- 脚注と文末脚注
- テキストボックス
- コメント
- ルビ、傍点などWord固有の高度な構造
- 埋め込みオブジェクト

## 既知の制約と危険箇所

- 入力・出力パスが特定環境に固定されている
- 数字と英字を文脈に関係なく一律変換する
- 日付、時刻、型番、URL、メールアドレス、単位付き数値なども変換対象になりうる
- 5桁以上の数字は変換関数の想定範囲外
- Run境界をまたぐ文字列は正しく検出できない
- 見出し判定は段落スタイル名に依存する
- 本文のフォントサイズを一律12ptにするため、意図したサイズ差を失う可能性がある
- 斜体をすべて太字へ変更するため、意味上必要な斜体も失われる
- 表や脚注など文書全体を網羅していない
- 自動テストがない
- 変更内容のプレビューや差分レポートがない

## 次の設計方針

今後は、日本語小説原稿の入稿前チェックを行う「原稿プリフライトツール」として、次を優先します。

1. 変換ロジックとDOCX入出力を分離する
2. CLI引数で入力・出力ファイルを指定できるようにする
3. 元ファイルを上書きしない
4. 各変換ルールを個別に有効・無効化できるようにする
5. 誤変換しやすい箇所は自動修正ではなく警告として扱えるようにする
6. 数字、句読点、字下げ処理のユニットテストを追加する
7. dry-runや変更レポートを用意する
8. DOCXの書式と構造を保持できる範囲を検証する

設計と作業候補は [Issue #1](https://github.com/yo4e/docx-kanji-converter/issues/1) にまとめています。
